# 拾帧 FrameSeek

本地视频素材库：**按台词找时间点，一键导出该台词前后 N 秒片段。**  
素材目录选哪儿，索引就生成在哪儿 —— 选中文件夹后自动建 `.frameseek/` 隐藏目录，  
里面放 SQLite 索引、视频封面/动图、逐句台词截图和导出的片段。整个文件夹拷走，索引跟着走。

技术栈：Python + Flask（Web） + MCP（给 AI 客户端调用） + SQLite/FFmpeg。  
前端：**Vue 3 + Element Plus**（深色主题），依赖在 `web/vendor/` 本地自持，断网也能跑，
无构建步骤（浏览器里直接编译模板，改完刷新即生效）。

仓库：<https://gitee.com/LinYiSongEr/frameseek>

### 从仓库拉下来怎么跑

```bat
pip install -r requirements.txt      # flask / rapidocr-onnxruntime / mcp ...
python app.py                        # http://127.0.0.1:8771
```

第一次跑 OCR 会加载 RapidOCR 模型（几秒）。仓库里**不带**这些：

| 不入库的东西 | 为什么 |
| --- | --- |
| `hub.db` / `*.db` / `.frameseek/` | 本地索引，含你自己素材库的绝对路径 |
| `vendor/`（根级，约 259MB） | 本机 venv 里 anyio 半残才塞进去的依赖兜底，正常环境用 pip 装。注意 `web/vendor/` **入库**（Vue/Element Plus 本地依赖，约 1.7MB） |
| `AI生成/`（含 `绘画/` 子目录与 `手绘/` 工程） `_hd_src/` `_out/` | 产物与日志 |
| `_testlib/`（96MB 视频） | 回归脚本的测试素材，自备；没有它 UI 回归跑不起来，主程序不受影响 |

原单体 `web/app.js`（约 1600 行：全局状态 + 实时通道 + 7 个页面组件 + 主应用混在一起）
已拆成「**共享状态层 + 7 个功能模块 + 薄引导文件**」。后续改某一个小功能点只动对应文件，
不用翻整篇大文件、不浪费 token。

| `web/js/libs.js` | 模块 `libs`：素材库（登记/索引/上传/忽略名单 3 个 dialog），`FS.LibsView` |

| `web/js/gen.js` | 模块 `gen`：AI 生成（对话气泡进度），`FS.GenView`；`window.__FS.gen` |
| `web/js/handdraw.js` | 模块 `hd`：白板手绘（六步流程），`FS.HanddrawView`；`window.__FS.hd / hdApi` |
| `web/js/box.js` | 模块 `box`：方框复查（两级选片 / `SEQ` 代次号 / 指标表 / 三路修复），`FS.BoxView`；`window.__FS.box` |
| `web/js/clips.js` | 模块 `clips`：片段列表，`FS.ClipsView` |
| `web/style.css` | Element Plus dark 变量覆盖 + 布局样式 |
| `web/vendor/` | vue 3.5 / element-plus 2.9 / 中文语言包 / 图标，本地文件 |

**解耦方式**：`window.FS` 作为共享命名空间——`state.js` 挂 `S/BUS/LIVE/api/post/...` 等全局依赖，
各功能模块 `(function(){ const FS = window.FS; ... })()` 从 `FS` 取依赖、把组件挂回 `FS.XxxView`。
`index.html` 底部按序加载：vue → element-plus → zh-cn → icons → `state.js` → 7 个模块 → `app.js`。
后端 `app.py` 新增 `GET /js/<path:name>` 路由（目录穿越防护 + mime 映射），`index()` 给每个 js 模块
带 `?v={mtime}` 版本号防旧标签缓存。

模块 ↔ 组件：`libs` 素材库、`search` 台词检索、`assets` 素材（多维筛选）、
`gen` AI 生成（对话窗）、`hd` 白板手绘（六步）、`box` 方框复查、`clips` 片段。
页签切换用 `<keep-alive>`——方框复查一部片的清单要 verify 几秒，切回来必须秒开。

回归脚本通过 `window.__FS`（S / api / post / box / gen / hd）驱动页面状态，
UI 交互一律走真实 Element Plus 控件（点 checkbox、点 el-select 的 wrapper 弹 popper）。

## 0. 两级库（多素材库）

可以登记**任意多个**素材文件夹：

| 库    | 位置                             | 存什么                                            |
| ---- | ------------------------------ | ---------------------------------------------- |
| 库登记表 | **项目目录 `hub.db`**              | `libraries` 表：登记了哪些素材文件夹 + `settings` 表：当前库、开关 |
| 素材索引 | `<每个素材目录>\.frameseek\index.db` | 该目录自己的视频/台词索引，**随素材走**                         |

`hub.db` 的表：

```sql
CREATE TABLE libraries(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,            -- 备注名（默认取文件夹名）
  path TEXT NOT NULL UNIQUE,     -- 素材文件夹绝对路径
  enabled INTEGER DEFAULT 1,
  note TEXT DEFAULT '',
  created_at REAL,
  last_scan_at REAL
);
CREATE TABLE settings(key TEXT PRIMARY KEY, value TEXT);  -- active_id / use_asr / with_gif
```

页面上是一张表：名称 / 路径 / 素材数 / 台词数 / 总时长 / 上次索引 / 状态 / 操作（切换·索引·打开·删除）。  
**搜索默认跨全部素材库**（结果行标着来自哪个库），也可以切"仅当前库"。  
上传、视频列表、导出片段都作用于当前选中的那个库。

## 0.5 AI 生成产物单独一档（2026-10-15）

生成物**不进素材库、也不进台词体系**——它自己一档：

| 项        | 素材库                            | AI 生成产物                              |
| -------- | ------------------------------ | ------------------------------------ |
| 落点       | 用户登记的任意目录                      | `<项目根>/AI生成/`（hub 设置 `gen_outdir` 可改）  |
| 登记       | 写进 `hub.db.libraries`          | 不登记，`list_all()` 里凭空合成一条 `id=0` 内置只读 |
| 索引       | md5 + 封面/动图 + 台词（srt→内嵌→OCR）   | **只登记媒体信息**，台词恒为 0，`line_source='none'` |
| 页面入口     | 素材库卡片可索引/改名/删除                 | 素材页筛选里「🔒 AI 生成」可勾选，卡片菜单无台词类入口       |
| 台词筛选     | 有台词/没台词/识别失败                   | 不参与（AI 片不受这项筛选影响）                    |

隔离是**双保险**：

- 前端：AI 片卡片显示「AI 生成」标记而不是「没台词」，三点菜单只留 预览 / 打开文件夹 / 从库中移除 / 删除；
- 后端：`/api/video/retranscribe`、`/api/video/transcribe_asr`、`/api/video/reimport` 命中 AI 目录直接 400；
- MCP：`frameseek_add_library` / `retranscribe` / `transcribe_asr` / `recog_line` / `edit_line` /
  `verify` / `boxaudit` / `export_clip` 一律挡回，`frameseek_scan` 走 `no_lines` 只登记媒体信息；
- 自愈：早先按普通库索引过、留下台词的 AI 片，下次索引会清空台词（含 FTS）并置 `line_source='none'`。

实现就一个开关：`Indexer(..., no_lines=True)`（`core/indexer.py`）——跳过
`asr.get_lines`，不读同名 srt、不读内嵌字幕、不 OCR、不落 srt。
回归：`python _ai_isolate_ui_check.py`（12 项）。

## 1. 启动

```bat
双击  启动服务.bat
:: 或
python app.py          # 默认 http://127.0.0.1:8771
```

`启动服务.bat` 的行为：服务就绪后由 `app.py` 自己打开浏览器（脚本不提前开，

**关掉那个黑窗口 = 停止服务**。

> `set` 之类的行整段失效），并且**不要 `chcp 65001`**——改代码页会让 cmd
> 按字节偏移寻址错位，中文行会被从中间截断。所以要中文提示就存成 GBK，
> 否则正文用纯 ASCII。`.gitattributes` 已固定 `*.bat text eol=crlf`。

### 页面模块（顶部导航）

| 模块       | 干什么                                                             |
| -------- | --------------------------------------------------------------- |
| **素材库**  | 登记多个素材文件夹；每行操作：索引（弹设置→确认→下方显示进度百分比）/ 上传（弹窗拖放）/ 打开目录 / 删除登记。跑到一半可在右下角浮窗点**「停止」**，下次索引接着跑（见 §4）      |
| **台词检索** | 默认跨全部库搜台词，结果带截图+时间码+所属库；设前后秒数，一键「±片段」                           |
| **素材**   | 跨库浏览全部视频（缩略图悬停播动图）。点卡片预览；右上角 **···** 可打开所在文件夹 / 从库中移除 / 删除素材及文件 |
| **片段**   | 本次导出的 mp4 列表，可预览/下载/打开所在文件夹                                     |
| **生成**   | 对话窗口：输入文案 → 本地 MiniMax H3 生成视频 → 落入项目「AI生成」目录（详见 §5.6）。**成片不进台词体系**：不读字幕、不 OCR、不语音识别 |
| **手绘**   | 文稿 → 分幕 → 线稿 → 区域标注 → 逐笔渲染 → 配音合成（详见 §5.7）                |
| **方框复查** | 逐句核对台词的画面方框圈得对不对；可重新 OCR / 语音识别 / 直接编辑台词（详见 §5.5）  |
| **片段**   | 本次导出的 mp4 列表，可预览/下载/打开所在文件夹                                     |

没有"当前库"概念：搜索、素材浏览都跨全部库；上传和索引从表格行内发起，天然指定了是哪个库。

每个按钮都自带悬停说明（鼠标停一秒出），所以没有单独的"怎么用"页面。

删除素材有两种，都在卡片「···」菜单里（接口 `POST /api/video/delete`，参数 `root` / `video_id` / `delete_file`）：

| 菜单项     | 行为                                                                        |
| ------- | ------------------------------------------------------------------------- |
| 从库中移除   | 只删索引记录 + 封面/动图/台词截图，磁盘原文件保留。**同时把这个 md5 写进该库的 `ignored` 表**，以后再索引也不会把它收回来 |
| 删除素材及文件 | 上面这些 + 视频原文件 + 同名外挂字幕（.srt/.ass/.ssa/.vtt）。**要连点两次确认按钮才执行**，删除不进回收站       |

> 文件删除只在素材库目录内生效（后端用路径前缀校验，越权返回 403）。

被忽略的素材可在「素材库」表格里点 **忽略 N** 查看，逐个「放回」或「全部放回」，放回后下次索引会重新入库。

删除**素材库**只是摘掉 `hub.db` 里的登记记录：素材文件、`.frameseek/index.db` 全部保留，重新登记回来索引还在。

> 页面里的确认框都是自绘弹窗，**没用原生 `confirm()` / `alert()`**——同一页面反复弹原生对话框后浏览器会「阻止此页面创建更多对话框」，之后 `confirm()` 直接返回 false，删除就变成"点了没反应"。

## 2. 用法（Web）

1. 顶部填素材文件夹绝对路径（可顺手起个备注名）→ **＋ 登记素材库**（此时该目录下已生成 `.frameseek/`）
2. 重复登记同一路径不会重复；再登记一次并填新名字可以改名
3. 表格里点 **索引**（单个库）或 **索引全部**
4. 也可以直接把视频拖到页面上传，文件落到 `.frameseek\uploads\` 并自动入库
5. 右边搜台词（中文子串也能搜）→ 结果带**截图 + 时间码**
   - **预览**：播放器直接跳到该句前 2 秒开播
   - **±片段**：导出该句前 5 秒 + 后 5 秒（秒数可在页面改）的 mp4，落到 `.frameseek\clips\`
6. 视频列表悬停缩略图 → 自动播放动图预览

选项：**无字幕时语音转写**（faster-whisper，慢，可关）、**生成动图预览**（关掉索引更快）。

## 4. 台词从哪来（优先级）

| 顺序 | 来源                            | 速度  | 说明                                  |
| -- | ----------------------------- | --- | ----------------------------------- |
| 1  | 同名外挂字幕 `.srt/.ass/.ssa/.vtt`  | 毫秒  | 视频旁边放同名字幕即可                         |
| 2  | 内嵌字幕流（`ffmpeg -map 0:s`）      | 秒级  | mkv/mp4 内封的字幕                       |
| 3  | **OCR 硬字幕识别**（RapidOCR，默认 DML 走 GPU） | 分钟级 | 看画面认字，4 进程约 7 倍实时（2026-10 调优后 + DML） |
| —  | faster-whisper 语音转写           | 已停用 | 保留代码兜底，`config.ASR_ENABLED = False` |

全文索引用 SQLite FTS5 **trigram**，所以"思念""茶花"这种两字中文也能命中（<3 字自动退回 LIKE）。

### OCR 只要字幕本身：三层净化

RapidOCR 认的是"画面里所有字"，不是"台词"。直接用会混进一堆东西。  
实测 8 部片子，噪声有四类（括号里是实际识别到的样本）：

| 噪声          | 实测样本                              | 处理手段                                |
| ----------- | --------------------------------- | ----------------------------------- |
| 一帧多个框被直接拼一起 | 「开战已经是箭在弦上了…」+「決定の真面」（《云之彼端》中日双语） | 同帧内字号更小 **且** 置信度更低的那行判为附加语种，丢掉     |
| 片内 UI / 数字屏 | 「0663 1.00」（《名侦探柯南》）              | 纯数字/编号正则                            |
| 角落台标、底部水印   | 贴边或横贯全宽                           | 几何判据：不居中 / 贴边 / 宽度过大                |
| 片头演职员表      | 「镇衡主演」「李麗麗友情客串」「張國榮 領銜主演」         | 工种词 + 人名的结构判定（正则做不了，见 `_is_credit`） |

核心是 `core/ocr.py` 的两个函数：

**`calibrate()`** —— 开跑前花十几秒做两件事：整片均匀撒 20 个点，  
每点抽一帧 OCR 一次，统计框都堆在哪个纵向区间，得出这部片的**字幕位置画像**  
（`SubtitleProfile`：字幕带上下沿、典型字高、置信度基线、假名率）。

为什么必须每部片单独标定：字幕基线是压制组决定的，各片差异明显——  
港片实测 y≈0.77、日漫 y≈0.66~0.70，写死一个折中窗口两头都不讨好。  
而双语片一帧两行（中文行 cy=0.68、日文行 cy=0.86），用全体中位数算带心  
会正好卡在两峰中间，把两行都圈进来；改成取**直方图最高桶**才收紧得下来。

**`select_subtitle()`** —— 每帧只保留"像字幕的那一行"，五道几何关卡：  
水平居中（±0.22）、不贴边（离左右边≥0.03）、宽度 8%~~88%、  
字高接近该片标定值（0.55~~1.9 倍）、纵向落在标定带内。  
再用 `_strict` 之外的 `_tidy` 做文本清洗，最后内容级过滤 `_is_credit`。

实测结果（8 部片子）：正常台词**零误杀**，双语行的日文部分已能剔除。

### 性能：像素不是瓶颈，线程才是（2026-10 实测）

拿 5 分钟片段（1920×1080，0.5s 网格 = 600 帧）做对照实验，结论和直觉相反：

| 送检像素             | 单帧耗时（单进程） | 说明                            |
| ---------------- | --------- | ----------------------------- |
| 960×162（155k px） | 111 ms    | 当前配置                          |
| 736×124（91k px）  | 132 ms    | 像素少了 40%，反而更慢（噪声内）            |
| 480×80（38k px）   | 79 ms     | 像素只剩 1/4，只快 29%，字高掉到 15px 开始崩 |
| 960×108，无字幕帧     | **14 ms** | 只检测不识别——**识别（rec）才是成本大头**     |

也就是说：**靠降分辨率提速走不通**。成本大头是识别（每个框固定 48×320 输入，  
跟图多大没关系），检测只占 14ms。像素从 155k 砍到 38k 只省 29%，却要赔上识别质量。

真正的瓶颈在并行：**每个 OCR 子进程的 onnxruntime 没限线程数，默认开满 16 个线程**，  
8 进程 × 16 = 128 个线程抢 16 核。实测同样的 600 帧：

| 并行方式               | 600 帧识别段        | 端到端（含标定 18s + 抽帧 8s） |
| ------------------ | --------------- | -------------------- |
| 8 进程 × 16 线程（修复前）  | 180 s           | **206 s**            |
| 1 进程 × 2 线程        | 15.5 s（120 帧口径） | —                    |
| 4 进程 × 2 线程（修复后默认） | ~24 s           | **28 s**             |
| 8 进程 × 2 线程        | ~25 s           | 比 4 进程只快 6%，不值得      |

修法在 `core/ocr.py` 的 `_apply_threads()`：onnxruntime 1.29 **没有** `set_session_options`，  
线程数只能在建 session 那一刻定，而 vendor 的 `OrtInferSession` 是  
`from onnxruntime import InferenceSession` 直接绑名字，patch `onnxruntime` 模块属性无效，  
得换成 `rapidocr_onnxruntime.utils.InferenceSession` 自己那个引用。

**最终效果：5 分钟片段 206.5s → 27.7s（7.5 倍），102 条 / 860 字与修复前完全一致。**

试过但**否决**的两条（数据在 `_out/`，脚本 `_bench_seq.py` / `_analyze_seq.py`）：

- **"同一句字幕还在，就跳过识别"**：对检测框 crop 出来的图缩到 64×16 做平均绝对差，  
  同一句相邻帧 MAD p50=23.6，不同句 min=22.8 —— **两类完全重叠**，阈值 20 也只能跳过 16%  
  且开始误判。字幕在淡入淡出、背景从字缝里透出来，0.5s 间隔像素已经变了。
- **降分辨率/收窄字幕带提速**：收益见上表，且收窄带要联动改几何阈值，性价比不高。

真正还能再压的是固定成本：**标定要 18 秒**（20 次独立 ffmpeg seek，每次解一帧），  
改成一次解码撒 20 帧能省 15 秒——但只对 5 分钟这种短片有意义，整部电影可忽略。

### 把 GPU 拉进来：DirectML provider（2026-10 接入）

OCR 原本纯 CPU 跑（vendor 的 onnxruntime 是 CPU-only build，provider 里根本没有 GPU）。
现在默认走 **DML**：`vendor/ort_dml/` 里放了 onnxruntime-directml 1.24.4
（DML 独立发行版的最后版本，73MB），`core/ocr.py` 的 `_setup_dml()` 在引擎构建前
把它插到 `sys.path` 最前，阴影掉 venv 里的 CPU 版——**必须在任何代码 import
onnxruntime 之前做**，`sys.modules` 缓存后换包会静默失效。注入点在
`_apply_threads` 的 `TunedSession`（线程数同样只能在建 session 那一刻定），
providers 最前加 `DmlExecutionProvider` 即可，ORT 按顺序初始化，失败自动落 CPU。

收益（亮剑 01.mp4，3840×2880，走 app 自己代码路径实测）：

| 口径 | CPU | DML | 加速 |
|---|---|---|---|
| 单进程 det / rec | 29ms / 88ms | **14ms / 63ms** | 1.41× |
| 4 进程 ×2 线程池吞吐 | 41.6 帧/s | **53.5 帧/s** | 1.29× |
| 识别质量 | — | **9 条台词逐条一致** | — |

收益边界：rec 输入是 48×320 的单行小图，kernel launch 开销吃掉大半收益
（det 1.8×，rec 只 1.2×）；四个进程抢一块 4060Ti，池级只剩 1.29×。
开关：`config.OCR_USE_DML`（默认开），环境变量 `FRAMESEEK_OCR_DML=0` 可临时反转做 A/B。
包缺失/provider 不可用/onnxruntime 已被 import 时自动退回 CPU，不影响识别结果。
worker 启动日志会打 `provider=dml|cpu`，服务日志可直接核对。

### 高分辨率片先压 1080p 代理再抽帧（2026-10 新增）

ffmpeg 有个绕不过去的事实：**解码器永远吐原生分辨率帧，`scale` 滤镜在解码
之后**。所以滤镜链里写得再狠，4K 该解的像素一帧都不会少。而 OCR 流式管道
恰恰是最吃亏的——命令是 `-i → -vf crop,scale → rawvideo`，**全帧解码一帧不跳**，
Python 端才按 `OCR_STEP` 网格丢帧，等于 4K 片有 80% 的帧"解完就扔"。

唯一的解法是让 ffmpeg 只解码一次：先转一份 1080p 代理，之后 OCR 流、台词截图、
重扫全部读代理。

**触发条件只看分辨率**（`config.PROXY_TRIGGER_PIXELS`，默认 1920×1080 严格大于）：
电视剧库 28 部全是 **3840×2880**，像素量是 1080p 的 5.3 倍；电影库 64 部全部
≤1920 宽，一部都不会触发。

| 环节 | 读哪个 |
| ---- | ---- |
| md5 / 元信息 / 封面 / 动图 | 原片 |
| 外挂 SRT / 内嵌字幕流 / 语音转写 | 原片（外挂 srt 就贴在原片旁边，代理里没有字幕流） |
| **OCR 帧流 / 台词截图 / 重扫** | **代理** |

画质基本无损，所以只赚时间不亏质量：OCR 送检带宽固定 `OCR_WIDTH=960`，
3840×2880 的底部 30% 裁带缩到 960 与 1920×1440 裁带缩到 960 **尺寸完全相同**
（只是多一次重采样），文本结果不受影响；台词截图固定 `SHOT_WIDTH=480`，
源是 4K 还是 1080p 出来的图基本一样。

配套细节：

- **只在真的需要 OCR 时才建（惰性）**。台词优先级是
  `外挂 SRT → 内嵌字幕流 → OCR → ASR`，前两级命中就**根本不建代理**。
  这个坑踩过：原先是无条件先建代理再取台词，结果《潜伏》这种**内嵌了
  subrip 字幕流的 4K 片**（3136×2160 HEVC 10bit，2 条字幕流各 2556 行，
  简体流第 2 条就是"据我所知啊/参加旧金山会议的代表"）也被先压了一遍
  888MB 代理，**白花 7 分钟**——而它 1.4 秒就能拿到 639 条字幕，压根不需要 OCR。
  现在的判断只做廉价探测（外挂文件 stat + ffprobe 的字幕流列表），0.000 秒出结果。
- **转码要有进度反馈**。ffmpeg 默认只在 stderr 吐静态统计，而我们 `-v error`
  把它们全关了，转码阶段对前端**完全静默**——用户看到界面几分钟没动静就以为
  卡死（这个坑也踩过）。现在开 `-progress pipe:1` 边读边推百分比，
  实测 10bit 整部 432 秒全程 0%→100% 实时递增（按 2% 一跳，避免刷屏）。
- **存放** `.frameseek/proxy/`——放缓存目录里的关键原因是 `list_video_files`
  会整体排除 `CACHE_DIR`，代理天然不会被扫进库、不会被"重新索引"当成新片。
- **有效期** 代理与原片时长差超过 `PROXY_DUR_TOL`（0.5s）即视为过期并重建。
  这条不能省：拿一份时长对不上的代理去抽帧，末尾台词的时间点会落在代理时长
  之外，全部抽不到图。
- **转码三级降级** GPU 全链路 → CPU 软解+nvenc → libx264 ultrafast，
  任一级失败自动降级，建失败就删掉半成品回落读原片。
- **零风险** 代理是纯优化：开关关、片子本就 ≤1080p、有现成字幕、转码失败、
  异常抛出——六种情况全部回落读原片，不改变任何现有行为。

**提速 3.6 倍：把解码和缩放也搬上 GPU（2026-10）**

原先只有**编码**在GPU 上，解码 4K HEVC 和 lanczos 缩放都还在CPU 上跑，
而这两步恰好是慢的。瓶颈定位（3136×2160 HEVC Main10，180 秒切片，4060Ti/16核）：

| 方案 | 耗时 | 实时倍率 | 说明 |
| ---- | ---- | ---- | ---- |
| CPU 解码 + lanczos + nvenc（改造前） | 34.0s | x5.3 | 只编码在 GPU |
| CPU 解码 + bicubic + nvenc | 31.8s | x5.7 | 只换插值质量，**只快 6%** |
| **NVDEC + scale_cuda + nvenc** | **7.2s** | **x24.9** | 解码/缩放/编码全在 GPU |
| 并行 2~6 段 · GPU | 7.3~8.0s | x22~25 | GPU 已吃满，分段无收益 |

第二行是关键证据：**换缩放算法几乎没用，说明瓶颈根本不在缩放，而在 CPU 软解码**。
所以提速 4.7 倍的正解是 NVDEC，而不是去调 lanczos。

**GPU 缩放的插值必须显式指定（踩过的坑）**：`scale_cuda` 的 `interp_algo` 默认是
**nearest**，会**丢台词**。亮剑真烧录字幕片上跑 OCR 端到端（真实入口 `ocr_lines`，
90 秒片段，3840×2880）：

| 代理插值 | 像素 PSNR | OCR 台词 | 丢失 | 新增 |
| -------- | --------- | -------- | ---- | ---- |
| CPU lanczos（基准） | — | 14 条 | — | — |
| cuda nearest（默认） | 37.8 dB | 14 条 | **2** | 2 |
| cuda bilinear | 41.1 dB | 14 条 | 1 | 1 |
| **cuda bicubic** | **41.1 dB** | **14 条** | **0** | **0** |
| cuda lanczos | 40.0 dB | 15 条 | 0 | 1（多识别一条） |

`bicubic` 与 CPU lanczos 的 OCR 结果**完全一致**，像素 PSNR 41.1 dB 属于视觉无损，
所以定为默认（`PROXY_CUDA_INTERP=3`）。

**GPU 路径绝对不能加 `-pix_fmt`（踩过的坑）**：`scale_cuda` 的 `format=nv12` 已经
定死输出格式，再加 `-pix_fmt nv12`（或 `yuv420p`）会让 `auto_scale` 介入协商并直接
失败：`Impossible to convert between the formats supported by Parsed_scale_cuda_0
and auto_scale_0`，整条转码 rc≠0。这个坑很阴——**它不是启动时报错，而是产出 0 字节
文件后靠降级链静默回落到 CPU**，实测整片耗时从 143s 悄悄变成 400s，日志上完全看不出
走过 GPU。所以 GPU 路径干脆不给 `-pix_fmt`，让编码器直接吃 nv12。

**降级链的必要性**：实测同一部片子 GPU 路径失败（0.8s / 0MB）时，全靠自动降级到
CPU 软解才拿到结果。任何驱动/滤镜差异都不能让代理功能整体挂掉。

实测（亮剑 01.mp4 整片，3840×2880 HEVC 8bit，43.6 分钟）：

| 口径 | 改造前 | GPU 全链路 |
| ---- | ------ | ---------- |
| 触发判断 | 11059200 像素 > 2073600 → 建代理 ✅ | 同左 |
| 转码耗时 | 383~400 秒 | **141~143 秒（2.4 分钟）** |
| 实时倍率 | x6.5 | **x18.5** |
| 代理体积 | 801MB / 2.57Mbps | 801MB（码率封顶，体积不变） |
| 代理规格 | 1920×1440 yuv420p | 1920×1440 yuv420p（一致） |
| 二次调用 | 秒回 | 0.16s（幂等命中） |

实测（潜伏 S01E01 整片，3136×2160 HEVC **10bit**，45 分钟，**内嵌字幕流**）：

| 口径 | 结果 |
| ---- | ---- |
| 字幕流 | 2 条 subrip（流2 简体 / 流3 繁体，各 2556 行） |
| `from_embedded` | **1.4 秒拿到 639 条**，首条"据我所知啊" |
| 代理判断 | 0.000 秒 → **不建代理**（有字幕就不需要 OCR） |
| （对照）真要转 10bit 源 | 约 70 秒 / 888MB，**37 倍实时**，10bit 无额外开销 |

**码率必须有上限（踩过的坑）**：最初写成 `-rc vbr -cq 23 -b:v 0`，以为 CQ 会自己
收敛，实际 `-b:v 0` 在 VBR 下等于**放弃码率约束**——nvenc 一路推高码率，把 43 分钟
的 3840×2880 压成 **2.9GB**（约 9Mbps）的大文件。大代理 + 5倍解码量叠加，扫描
电视剧库时把服务进程压到 **Segmentation fault**（整个 Flask 服务挂掉，不是普通异常）。
两个小样本测试（180秒片段）完全掩盖了这个问题——体积随码率线性放大，样本小了看不出来。

现在三重约束：

| 参数 | 值 | 作用 |
| ---- | ---- | ---- |
| `PROXY_MAXRATE` | `2500k` | `-maxrate/-bufsize` 码率天花板，CQ 仍主导画质。2.5Mbps 对 960 宽的字幕带识别绰绰有余 |
| `PROXY_MAX_MB` | `1500` | 代理体积硬上限，超了判死重建——第二道保险，防编码器再次失控 |
| `PROXY_DUR_TOL` | `0.5` | 时长差超限判过期（防止末尾台词时间点落在代理时长外，抽不到图） |

### 标定缓存：同一剧集只标定一次（2026-10）

识别任何一部片之前，都要先**标定字幕带**：整片均匀撒 20 个点，每点抽一帧跑一次
OCR，统计框都堆在哪个纵向区间、字高多少、置信度基线、字体指纹。这一步决定
后续几何筛选的松紧——港片字幕带中心 y≈0.77、日漫 y≈0.66，不标定就只能写死一个
折中窗口，两头都不讨好。

**成本是每部必付的固定税**：20 次 `-ss seek + 单帧 OCR`，实测约 **23 秒/部**。
而同一剧集各集的字幕带位置、字高、字体指纹**几乎完全相同**（同一压制组、
同一版式），27 部《亮剑》重复做26 次纯粹是浪费。

标定结果现在落盘到 `<库>/.frameseek/calib/<键>.json`，键是：

```
<宽>x<高>_<编码>_<OCR_WIDTH>_<OCR_BAND>_<OCR_STEP>
例：3840x2880_hevc_960_0.300_0.2
```

**键的设计是关键**，两个坑：

- **不能用文件 md5** —— 那样每部片一个独立键，缓存等于没做。
- **不能只按目录** —— 同目录下可能有不同分辨率的片，带位置会差。分辨率必须进键：
  字幕带的**归一化**坐标依赖裁带比例，4:3（3840×2880）和 16:9（1920×1080）
  裁同样 30% 带，字高归一化后不同。编码也要进键：H.264 与 HEVC 的压制位置
  常差几行，混用会让标定带偏，**直接导致整片认不出**（比慢更糟）。
- **键里不能有 Windows 保留字符**（`| < > : " / \ ? *`）。踩过：分隔符用 `|`
  直接 PermissionError，缓存永远写不出来，而写入处的 `try/except` 把异常
  吞了，表面看只是"怎么没变快"。现在分隔符用 `_`，且写入失败会打一行日志。

只有 `ok=True`（样本 ≥6 个框）的标定才写入缓存，失败的不写——避免把坏结果
固化下来反复命中。`calib_cache_clear(video)` 可清空某个库的缓存。

实测（亮剑 26.mp4）：

| 项 | 首次 | 命中缓存 |
| --- | --- | --- |
| 标定耗时 | 23.6 秒 | **0.46 秒**（51×） |
| 同剧另一集（27.mp4） | — | **0.47 秒** |
| 识别结果 | — | 逐条完全一致 |

### 解码/OCR 并行：实测无效，代码保留但默认关闭（2026-10）

`_frame_stream` 原本在主线程里迭代，每攒满 24 帧调一次阻塞的 `pool.imap`——
OCR 算这批的工夫主线程没去读管道，ffmpeg 的 stdout 缓冲一满就自己阻塞，
于是解码和 OCR 串行相加。看数据像是能省一大截（管道单独跑 46 帧/秒，
是 OCR 的两倍），于是实现了 `_FrameFeeder`：生产线程预读帧进有界队列，
主线程只消费，真并行。

**实测整部（亮剑 26.mp4，同一台机器连续跑）：**

| 模式 | 耗时 | 条数 |
| ---- | ---- | ---- |
| 串行（改造前） | **924.1 秒** | 871 |
| 并行（feeder） | **935.1 秒** | 871 |

**没有任何收益**，差异 11 秒在噪声内。原因：解码占的CPU 核，OCR 占的也是
CPU 核 + DML，16 核不够两边同时跑满——管道那"两倍富余"是空闲时的富余，
机器一忙就没了。

教训：**动手前应该先测基线可复现性**。这个改造的判断依据是一组 624.5 秒的
数据，复现时却是 924 秒——那 624 秒是机器空闲时的偶然值。一旦真去复测，
"解码 278s + OCR 397s 串行相加"这套拆解就站不住了（那是公式倒推，不是实测），
真正的结论是 OCR 计算本身就是瓶颈（稳态约 16 帧/秒）。

代码保留在 `core/ocr.py` 的 `_FrameFeeder`，由 `FRAMESEEK_OCR_PARALLEL=1`
开启，默认走串行。保留是因为：若将来换更强的 GPU、DML 占用率下降，
瓶颈分布可能反转，值得重新评估一次。

### 台词以"句"为单位：0.2s 网格 + 同句投票（2026-10 重做）

早期的台词本质是"每 0.5s 认一帧、相邻相似的并起来"，不是真正的句子：  
0.3~0.5s 的短对白会整句漏掉，时间边界有 ±0.25s 误差，而且整句文本取的是  
**第一帧**的识别结果——第一帧正好漏一个字，这句就永远缺字。

现在的做法（`OCR_STEP = 0.2`）：

1. **0.2s 采样网格**（每秒 5 帧）。一句 1.5~~3s 的台词被命中 8~~15 次，  
   0.4s 起的短句至少命中 2 帧，漏不掉；时间边界精确到 ±0.1s  
   （库里实测 min 0.5s / p50 1.5s / p90 2.5s，都是 0.2 的整数倍）。
2. **同句多帧投票**（`_pick_best`）。同句的识别变体按出现次数择优，  
   不再让第一帧的漏字版代表整句。平票取**短**——多出来的字往往是上一句  
   尾字或画面元素串入（实测出现过"祗可惜同床异梦""哗八个一起上吊"）。
3. **方框凭证校验位置**。`_similar` 的字符判据够松，相邻两句用词相近会  
   被并错；用"同一句话只可能出现在一个位置"兜底，框心飘了的帧不算  
   本句证据（这是方框复查模块的基础）。

实测对比（同一 5 分钟片段）：

| 步长                | 条数  | 字数      | 端到端      | 说明          |
| ----------------- | --- | ------- | -------- | ----------- |
| 0.5s（旧逻辑，首帧文本）    | 102 | 860     | 24 s     | 基线          |
| 0.5s + 投票         | 102 | 876     | 27 s     | 纯投票就补回 16 字 |
| **0.2s + 投票（当前）** | 102 | 866~870 | **42 s** | 边界更细、短句更保险  |

字数打平不代表质量打平——**目检截图证明 0.2s 更完整**：这部片里  
"祗可惜同床异梦"（11.0s）和"不怕一万，祗怕万一"（278.5s）两处，  
0.5s 版都漏了首字"祗"，0.2s 版抓到了（截图在 `_testlib/.frameseek/shots/`  
第 4、92 张，画面里"祗"字清晰可见）。

代价是帧数 2.5 倍：5 分钟 42 秒，1 小时电影约 8~~9 分钟。要更快就把  
`OCR_STEP` 调回 0.5（基准脚本支持 `FRAMESEEK_STEP=0.5` 环境变量临时对比），  
但 0.3~~0.5s 的短对白会开始整句漏掉。单帧识别错误（"少爷"↔"少餐"、  
"夫人"↔"失人"这类单字抖动）投票也修不了，属于 OCR 模型本身的极限，  
可在台词页面直接编辑。

#### 净化阈值表（在 `core/config.py`）

判定"附加语种行"的两条（`OCR_H_RATIO_DROP` / `OCR_CONF_RATIO_DROP`）要**同时**成立  
才丢一行——单条都会误杀长句折行字幕（实测《天气之子》折行第二行字高比 1.20、  
置信度比 0.90，两个都不低于门槛，全部保留）。

### 字体指纹：每条字幕记下"字长什么样"

方框凭证回答"画面上有没有一个框"，但回答不了"框里的字是不是本部片的那套字体"。  
一部片子的字幕由同一个压制组用同一套字体做成，指纹在片内高度稳定；而 OCR 串行、  
单帧误检、水印台标，往往是另一套字体或另一种字号。所以每条字幕入库时都带一份  
**字体指纹**（`lines.box.font`）：

| 字段         | 含义                         | 实测（《唐伯虎点秋香》5 分钟）         |
| ---------- | -------------------------- | ------------------------ |
| `ink`      | 墨密度：字像素占框区面积比（Otsu 自适应二值化） | p50 0.20，p90 0.43        |
| `stroke`   | 笔画宽度：字像素横向游程均值（≥2px，滤毛边）   | p50 4.0px，p90 6.7px      |
| `px_h`     | 字高占整幅画面比例（跨分辨率可比）          | p50 7.8%                 |
| `font_dev` | 相对**全片台词分布**的偏离度（MAD 尺度）   | >1.5 为强异常，实测 102 条里 15 条 |

三个关键设计（都是踩坑换来的）：

1. **Otsu 阈值，不用 (max+min)/2**。字幕是白字黑描边，框里还裹着背景（柱子、  
   人脸，灰度中等）。固定比例阈值会把阈值推到背景之上，mask 只剩字芯，墨密度  
   被系统性低估（实测"将军令呀！"被算成 0.11，正常 0.2+）。
2. **游程取均值不取中位数**。中位数会被大量 1~2px 抗锯齿毛边主导，实测全体  
   退化成 2.0，没有判别力；只统计 ≥2px 游程再取均值才是真实笔画粗细。
3. **偏离度用全片分布做基准，不用标定样本**。标定只抽 17 个框且状态一致，  
   MAD 小到 0.01；而识别阶段跨几百秒，镜头运动、淡入淡出让指纹自然波动  
   （库内 ink 横跨 0.09~0.49）。拿小样本 MAD 当尺度，正常行全部被放大成  
   巨大偏离（实测 100% 超标）。所以 `_rebase_font()` 在识别全部完成后，  
   用 100+ 条台词的中位数 + MAD 重算每行的 `font_dev`——分布紧时敏感，  
   分布宽时放松，只抓真离群。

**只标不删**：偏离大的行不判伪（片头大字号、艺术字场景都会偏离——实测 top 3  
异常里就有宁王府段的大字号镜头，截图看字幕完全正常），而是进 `verify.check_line`  
的 `detail`（不进 reasons）、台词页显示琥珀色"字体异常"徽标、方框复查页指标表  
列出三项指纹值。纠错时先看这些行；二次验证时知道"这句的字和主流不一样"，  
它的方框证据权重降档。实测抓到的真问题：OCR 串行句"两家好八皮马四同四饮"  
（dev 4.0，stroke 9.2）、单帧短句"是啦"（dev 2.2，hits 3）。

### 方框校验：每条字幕都得有画面上的框撑着

前一层解决的是"这一帧挑哪个框"，但从单帧到入库还有一段路，  
中间有几处会让**文本和方框脱钩**：多帧合并靠字符集重合度（`_similar`），  
会把用词相近的相邻台词并成一条；文本可能被换成更长的那一条而方框没跟着换；  
边界帧（字幕淡入淡出）套的框比稳态松。所以入库的每一行现在都带一份  
**方框凭证**（`lines.box`，JSON），记录这个字幕是由哪些检测框拼成的：  
框位置、字高、置信度、字宽比、几个帧支持、跨帧漂移多少。

有了凭证才能反过来问一个文本永远回答不了的问题——  
**"这一帧的画面上，真有这么一个框吗？"** `core/verify.py` 分两级回答：

| 级别   | 函数              | 做什么            | 成本       |
| ---- | --------------- | -------------- | -------- |
| 凭证自检 | `check_line`    | 拿存下的凭证核它自身是否自洽 | 毫秒，全库可跑  |
| 现场复核 | `recheck_video` | 回到画面上重抽帧真找一遍框  | 分钟，能真正证伪 |

自检看七项，其中**字宽比**（`ar` = 框宽像素 ÷ (字数 × 字高像素)）判别力最强：  
真实字幕是方形字，每字宽度≈字高，所以这个值应该≈1。实测 6 部影片 95 个检测框，  
正样本 P05~~P95 = 0.73~~1.22，而识别串行、字形粘连的噪声能飙到 4.18。  
另外六项：跨帧漂移、覆盖率、置信度、水平居中、字高范围、框数。

覆盖率用「被认到的时长 ÷ 声称的时长」而不是「至少命中 N 帧」——  
只闪 0.8 秒的短台词在 0.5 秒网格上本来就只该命中一两帧，  
端到端实测《唐伯虎点秋香》60 秒片段里「有见地」「不要这样啦」这类  
3~5 字短台词就是 1 帧，用绝对阈值会把它们全判死。

**方框凭证反过来修了一个合并 bug。** 多帧合并原本只看文本像不像  
（`_similar`：字符集重合 ≥75%），够松——相邻两句用词相近就会被判成同一句。  
实测「祝兄你隔几天就一百几十两地输」紧跟「输光了又走来叫救命」，  
两句共享「输/了/来」等字，后一句的帧被算进了前一句的凭证，  
覆盖率一度算出 150%。现在改成**位置也要对得上**才收这一帧  
（`OCR_SAME_PLACE_TOL`：框心 x 差 ≤0.05）——同一部片里同一句话  
在连续帧里只待一个地方，框心飘了就说明这是另一句的框。

**来源不同，可信度不同**：外挂 SRT / 内嵌字幕 / 语音转写本来就不靠画面框，  
它们的行标记为「不适用」而不是「失败」，报告里单列——  
把"没框可查"混进"没通过"，真实的问题会被淹没。

命令行：

```bash
python -m core.verify "E:\视频\电影"                     # 全库自检
python -m core.verify "E:\视频\电影" --recheck           # 抽样现场复核
python -m core.verify "E:\视频\电影" --videos 功夫.mp4   # 只查某部
```

Web 端 `GET /api/lines/verify?root=…&video_id=…&check=1` 返回逐条结论；  
检索结果里每行会带一个标记：绿「方框已验」/ 红「方框异常」/ 灰「无框(正常)」，  
鼠标悬停能看到具体几何数值。


### 方框复查页：台词帧 / 台词框 / 文字

左侧导航「方框复查」是给"二次人工复查"用的：把**那一帧画面**、**画在画面上的框**、  
**框里认出来的字**三样摆在一起，一眼看出框画得对不对。

- **台词帧**：按台词中点抽一帧 960 宽 JPEG（`core/boxaudit.frame_jpg`，带缓存，不重复抽）。
- **台词框**：图上叠两层——蓝框＝库里存的方框凭证；
  绿/红虚线框＝这次重新识别出来的框。
  两个框分开就说明这条台词的框不稳。勾「叠识别框」可只留蓝框。
- **文字**：框上方印章是库里台词；右侧指标列出 cx/cy/框宽高/字宽比 ar/
  置信度/命中帧数 hits/跨帧漂移 drift/覆盖率 cov。

**选片（2026-10-15 加两级筛选）**：65 部片挤在一个下拉里找片子太难，所以顶部是
**素材库下拉 + 片名搜索框 + 片单下拉**：

| 控件 | 行为 |
| --- | --- |
| 库下拉 | `全部库（70）` / `电影（65）` / `测试库（5）`，括号里是该库有台词的片数 |
| 搜索框 | 按**片名或目录名**过滤（placeholder：搜索片名/目录…），边打边筛（防抖 120ms）；多个词用空格分隔，**全部命中才算** |
| 片单下拉 | 过滤后的片子，**二级目录带前缀**（`亮剑/05.mp4`）；全库模式下片名后标出库名，免得同名片分不清 |
| 命中计数 | 右侧 `命中 5 / 70 部`；筛没了显示「没有匹配的片子」并清空右侧面板 |

**二级目录前缀**（2026-10-15 加）：电视剧按季/集分目录时（`亮剑/01.mp4`、`亮剑/02.mp4`）
片单里原来只显示 `01.mp4`，几十集挤一起根本分不清。现在三处都带目录前缀：

| 位置 | 显示 |
| --- | --- |
| 片单下拉 | `亮剑/05.mp4 · 电视剧 · 无框 780/780` |
| 标题栏 | `方框复查 亮剑/05.mp4 · 1918 条台词` |
| 搜索框 | 输 `亮剑` 能把整个目录的片子筛出来（目录名参与匹配，不只是片名） |

前缀来自 `/api/boxaudit/library` 每条记录新增的 `rel` 字段（相对库根的路径，
和素材页卡片用的是同一口径）；无目录的片子 `rel` 就是文件名，显示不变。
搜索按「片名命中 **或** 目录命中」判定，所以输 `05` 命中片名、输 `亮剑` 命中目录。

筛选都在本地做——`/api/boxaudit/library` 只拉一次全量概览（一条 SQL 聚合，70 部也是秒回）。
当前选中的片子还在结果里就保持选中、不跳回第一条；被筛掉才换片。

清单支持按状态过滤（全部 / 可疑 / 无框），顶部给通过率与失败原因分布。
`↑`/`↓` 换句。

三条修复路径（按钮名都按"用户想做什么"来写，不按内部流程名）：

1. **重新 OCR 识别**：对这句取首/中/尾各 3 帧重跑 OCR，逐帧报"框对不对得上、
   文字对不上"（判据 `|Δcx| + |Δcy| ≤ BOX_LIVE_TOL`），报告里有具体 Δx / Δy。
   结果填进右侧「重新识别结果」栏，**不自动写库**。
2. **语音识别这句**：只抽这句区间前后各 0.6 秒的音频跑 faster-whisper，
   返回听到的文字（1~3 秒，首次要加载模型约 10 秒）。同样只报告不落库。
   适合画面没硬字幕、或怀疑当初是听错字的那些行。
3. **编辑台词**：改文字、改起止时间，勾选可同时把这次识别到的方框
   折成新凭证写回 `lines.box`（`fold_probe` 复用 OCR 同一套聚合口径，
   人工补的框和自动产出的框过同一套阈值）。三帧对不上就整体拒绝、什么都不改。

识别（1、2）只读不写，编辑（3）才落库——这个分工是刻意的：
自动把识别结果覆盖到人工校对过的台词上，是不能接受的行为。

接口：`GET /api/boxaudit/library`、`GET /api/boxaudit/list`、
`GET /api/boxaudit/frame`（出图）、`POST /api/boxaudit/probe`（重新 OCR 识别）、
`POST /api/boxaudit/asr`（单句语音识别）、`POST /api/boxaudit/edit`（改台词 / 写框）、
`POST /api/boxaudit/backfill`（只写框，页面已无入口，脚本仍可用）。

MCP 侧对应两个工具：`frameseek_recog_line(line_id, mode="ocr"|"asr")` 只识别不写库，
`frameseek_edit_line(line_id, text=, start=, end=, save_box=)` 负责落库。

> 索引/OCR 走多进程，在 Windows 上从脚本直接调必须包在 `if __name__ == "__main__":`  
> 里，否则 spawn 会递归启动报 *"an attempt has been made to start a new process…"*。

### 语音转写：GPU vs CPU（本机实测）

同一段 75 秒《功夫》对白，RTX 4060 Ti 8GB：

| 模式                 | 转写耗时   | 倍实时   | 条数 | 备注                 |
| ------------------ | ------ | ----- | -- | ------------------ |
| **GPU / float16**  | 2.8 s  | 27 倍  | 35 | 默认。短片段固定开销占比高，倍率偏低 |
| GPU / int8_float16 | 2.3 s  | 33 倍  | 29 | 最快，但漏句稍多           |
| CPU / int8         | 11.1 s | 6.6 倍 | 37 | 无 GPU 时兜底          |

**长音频才是真实水平**：整部《功夫》99 分钟 → GPU 转写 **100 秒**、853 条台词，即 **59 倍实时**；  
900 秒连续音频纯模型推理 81 倍。抽音频本身可忽略（900 秒音频 ffmpeg 只用 5.6 秒）。

→ 106 小时素材：语音识别约 **2 小时**（GPU）/ 约 18 小时（CPU）。

### 但索引 ≠ 转写：时间都花在哪

一部 100 分钟、约 1200 条台词的片子，完整索引各环节的实测成本：

| 环节          | 单部耗时                       | 65 部合计       | 说明                         |
| ----------- | -------------------------- | ------------ | -------------------------- |
| 语音识别（GPU）   | ~100 s                     | **~1.8 h**   | 已不是瓶颈                      |
| 台词截图抽帧      | 0.121 s/帧 × 1200 ≈ 2.4 min | **~~2~~3 h** | 并发 8 路后（串行 0.32 s/帧要 7 h+） |
| 封面 + 动图     | 数秒 ~ 数十秒                   | ~~0.5~~1 h   | 关掉「生成动图预览」可省               |
| 抽 md5 / 元信息 | 秒级                         | 可忽略          |                            |

也就是说：**转写快了之后，瓶颈转移到抽帧截图上了**（它是 ffmpeg 逐帧 seek，吃的是磁盘随机 I/O，  
GPU 帮不上忙，只能靠并发——8 并发实测提速 2.6 倍，再多也没用）。并发数在 `SHOT_WORKERS`。

设备选择写在 `core/config.py`：`ASR_DEVICE = "auto"`（先探 GPU，失败回 CPU）、`ASR_COMPUTE = "auto"`（GPU 上取 float16）。想强制 CPU 就改成 `ASR_DEVICE = "cpu"`。页面顶栏会显示当前用的是 GPU 还是 CPU，索引弹窗的耗时预估也跟着变。

GPU 的额外前提：ctranslate2 需要 **CUDA 12 运行时**（`cublas64_12.dll` 等），本机没装 CUDA Toolkit，所以借 Ollama 自带的那套（`...\Ollama\lib\ollama\cuda_v12`），由 `core/asr.py` 的 `_mount_cuda_dir()` 在进程内挂载（PATH 前置 + `add_dll_directory` + ctypes 绝对路径预加载，三重保险）。

两个本机坑，已在 `core/asr.py` 里绕开：

- **faster-whisper 1.2.1 与本机 `av 19.x` 不兼容**：它调 `av.open(..., metadata_errors=)`，高版本 av 已移除该参数，一转写就 `TypeError`。→ 不传文件路径，改用 ffmpeg 抽成 16k 单声道 `float32` ndarray 再喂模型。
- **huggingface.co 直连 502**（模型下不下来）。→ 走镜像 `HF_ENDPOINT=https://hf-mirror.com`。

| ---- | ---------------------------------------------------------- |
| 摘要行（收起时也可见） | `第 3/65 个 · 已出 73 条台词`；单素材重识别时是素材名                |
| **当前视频** | `▶ 亮剑/12.mp4`——**二级目录下显示相对路径**，一眼知道在弄哪部     |
| 主进度条 | 整库：`3/65 个素材`；单素材重识别：素材名                                   |
| 阶段标签 | 清理旧台词 / 字幕标定 / OCR 识别 / 截图分片                               |
| **已识别画面** | `已识别画面 1,234 帧 / 约 4,000 帧 · 31%`（数字用等宽，不跳动）     |
| 细进度条 | `OCR 识别 46% · 276/600 帧 · 已扫 138/300s · 已出 73 条 · 剩约 1 分钟` |
| 停止按钮 | 红色「停止」，见下一节                                           |

传输优先 WebSocket（装了 `flask_sock` 时），退化 SSE（`/api/events`），再退化轮询。  
OCR 进度**每 8 帧或每 2 秒**推一次——再密没有意义，反而刷屏。  
索引每开跑一部新片子会**先把当前文件名推给浮窗**再开工，不用等第一批进度才知道轮到谁；
同时把上一部的帧数/台词数清零，免得挂着旧数字看着像卡住了。

### 中途停止 + 下次接着跑（2026-10-15）

索引一部电影要几分钟到十几分钟，浮窗右上角的红色**「停止」**按钮随时可以叫停，
停止后**下次点「索引」会自己接着跑**，不用重头来。

| 环节 | 行为 |
| --- | --- |
| 停止信号 | `POST /api/scan/stop`（可带 `root` 精确指定哪个库；只有一个任务时可省略）→ 置 `threading.Event` |
| 生效时机 | OCR 在**每 8 帧 / 每 2 秒**的检查点收工，ASR 在**分块开头**看。所以点了之后 1~2 秒内停 |
| 已跑完的素材 | **原样留库**（台词、截图、封面、动图全都在） |
| 正在跑的那一条 | **不留半截台词**——OCR/ASR 检测到中断就返回空结果 + `"__cancelled__"`，该条被置回 `status='pending' / line_source='pending'`，素材页显示「· 待识别」，下次重跑 |
| 还没轮到的素材 | 不入表，下次照扫 |
| 任务状态 | `tasks.status = 'stopped'`（不是 `done`），摘要写清「完成 N 个 / 剩 M 个 / 几个识别到一半下次重跑」 |
| 怎么续跑 | 再点一次「索引」——md5 去重让已完成的全跳过（弹窗会提示"本轮跳过 N 个已完成的"），被中断的那条走重跑分支补上 |

这里的技术要害是**中断绝不能污染数据**：早期实现里 OCR 中断后会把扫了一半的 `rows` 当完整结果返回，
下游拿它落库 + 写同名 `.srt`，那部片就永远只剩前半句台词。所以 `core/ocr.py` 专门用
`was_cancelled` 标记分流，`core/asr.py` 见到 `"__cancelled__"` **不落库、不写 srt**。

单素材的「重新识别台词」「语音识别台词」同样可停（走 `_stop_single`，清空后中断就停在空状态，
下次重新跑一遍即可）。回归：`python _scanstop_ui_check.py`（16 项，真切 3 个片段跑完整流程）。

### 重新识别台词

「素材」页卡片 `··· → 重新识别台词`。它和首次索引的区别：

1. **先清空再识别**：旧台词行、全文索引行、旧截图一起清掉，再按当前逻辑重跑。  
   不清的话，上次 102 条、这次逻辑改完只出 80 条，剩下 22 条旧台词会原样留着，  
   看起来像"识别没生效"。
2. **忽略自己上次生成的 `.srt`**：OCR 跑完会在视频旁落同名 `.srt`（那是产物不是素材）。  
   重新识别时若还按"外挂字幕优先"读它，等于把旧结果原样读回来。  
   所以上一轮来源是 `ocr` 时弹窗会**默认勾上「强制重跑 OCR」**，勾了连内嵌字幕也跳过。
3. 收尾 toast 会报：清掉多少条旧台词、新出多少条、走的哪条来源。

> 代价：识别失败时旧台词已经没了。这是有意的——"重新识别"就是要最新结果，  
> 留着旧的混在一起更难判断哪条是对的。想秒级完成就给它放一个同名 `.srt` 再「重新导入字幕」。

### 语音识别台词（没有字幕的电影）

「素材」页卡片 `··· → 语音识别台词`。**和「重新识别」的区别：完全不碰优先级链**——  
不读同名 `.srt`、不读内嵌字幕、也不跑 OCR，直接听音轨转写。就是给"画面上没有  
字幕"（外语原版、字幕是认不出来的图片花字、压制组没烤字幕）的片子用的。

- 同样先清空旧台词（含旧截图）再转写，收尾 toast 报清了多少、新出多少
- 模型可选 tiny / base / small / medium，默认 small（tiny 快 3 倍但错字明显）；  
  模型文件在 `~/.cache/huggingface` 缓存，首次用某个型号才下载
- 设备自动探 GPU：本机走 4060Ti + Ollama 借来的 CUDA 12 运行时（`core/asr._mount_cuda_dir`），  
  探不到自动退 CPU；弹窗里会显示当前设备与耗时粗估（GPU small 约 10 倍实时）
- 转写完在视频同目录落同名 `.srt`——whisper 的错字（"同床异谋"这种）直接在  
  srt 里改，改完点「重新导入同名 SRT」秒级刷新，不用再转写
- API：`POST /api/video/transcribe_asr`（root / video_id / model）；  
  设备现状：`GET /api/asr/info`

> 5 分钟测试片段实测：GPU small 全链路（清空 → 转写 → 截图 → srt）约 90 秒，  
> 出 106 条 / 717 字；同一部片 OCR 出 102 条 / 866 字——**两条路是互补的**：  
> 有字幕的片子 OCR 更准（文字是死的，没有听辨错误），没字幕的才需要语音。

- 已入库但没台词的，**下次索引默认重跑一遍**（弹窗「重新补一遍没有台词的素材」，默认勾选）；有台词的不会重复跑
- 单部片子可在「素材」页卡片「··· → 重新转写台词」单独跑；该页还有「只看没台词的」筛选
- 索引弹窗会按库总时长给出耗时预估

> 想快就给片子配同名 `.srt`——外挂字幕是毫秒级，跟语音转写不是一个量级。

## 5. 防重复

入库前算 md5（>512MB 的大文件走首/中/尾采样 + 文件大小，秒级）。  
同 md5 不会重复入库；如果原文件被移走，再次扫描会把记录迁到新路径，而不是新建一条。

## 5.6 AI 视频生成（对话窗口 → 项目「AI生成」目录）

顶部 **生成** 页是一个对话窗口：输入文案（Enter 发送）→ 生成带音频的 mp4 →
自动落入项目 `AI生成/` 目录（内置只读 AI 库，素材页可筛选到）。
成片**只登记媒体信息**（封面/动图/时长），**不做字幕和语音识别**——详见 §0.5。

**双后端（2026-10-18 加 Agnes，与生图的 `img_backend` 同构）**：

| backend | 引擎 | 分辨率 | 时长 | 速度 | 联网 | 说明 |
| -- | -- | -- | -- | -- | -- | -- |
| `agnes` | Agnes Video 2.5 Flash（API） | 1280×704 | 4~12 秒 | 数十秒~几分钟 | 要 | 默认优先，**成片自带音轨**；中文提示词可直接写 |
| `h3` | 本地 MiniMax H3 | 736×416（随像素档变） | 3~15 秒 | 5 秒约 10 分钟、10 秒约 40 分钟 | 不要 | 纯离线兜底，**独占 GPU**；英文提示词效果最好 |
| `auto` | 按 `agnes → h3` 降级 | — | — | — | — | **默认**。agnes 未就绪或失败才回落 H3 |

- `megapixels` 只对 H3 有意义；Agnes 固定 720P。
- `2:3` / `3:2` 两种宽高比**只有 H3 支持**，选 agnes 时会直接报错而不是静默降级。
- 显式指定 `backend` 时**不降级**——该后端失败就直接报错，避免"我以为走的云端，
  其实悄悄跑到了本地慢引擎"。
- H3 独占 GPU，两个 H3 任务由 `core/gen.py` 内的 `_H3_LOCK` 串行；云端任务不受此限，
  可与 H3 并行。

**架构 A：`h3` 后端（单服务 + 直调引擎，2026-10-14 定型，取代早前的双服务方案）**：

```
对话窗口 / MCP 工具
      │  prompt + 时长 + 宽高比 + 参考图
      ▼
core/gen.py ── spawn ──▶ h3gen.py（ComfyUI 便携版 python_embeded 独立进程）
                              │  import comfy.* 直接调节点函数，不起服务、不走 HTTP、
                              │  不加载工作流 JSON
                              ▼
                         UNETLoader → CLIPLoader(minimax) → VAELoader×2
                         → MiniMaxH3ReferenceToVideo → BasicScheduler(simple,12)
                         → SamplerCustomAdvanced → VAEDecode / VAEDecodeAudio
                         → ffmpeg 合成 mp4（绕开 SaveVideo 的序列化坑）
                              │  stdout JSON 行协议回报进度（phase/pct/done）
                              ▼
                         项目「AI生成/」目录 → 只登记媒体信息（不 OCR / 不 ASR）
```

**架构 B：`agnes` 后端（云端 API，2026-10-18 新增）**：

```
core/gen.py ── spawn ──▶ agnes_video.py（skill 脚本）
                            │  POST /v1/videos 建任务 → 2s 轮询 /agnesapi
                            │  → status=completed 时下载（自带 AAC 音轨）
                            ▼
                       项目「AI生成/」目录
```

 Agnes 那条线**不走 JSON 行协议**（脚本是提交+轮询+下载一体），所以进度是伪进度：
提交后推到 92%，下载完收尾。

要点 / 硬约束（H3 后端）：

| 项 | 值 |
| -- | -- |
| 引擎 | `h3gen.py`，用 `ComfyUI_windows_portable\python_embeded\python.exe` 跑 |
| 模型 | H3 ref2va int8 + Qwen3-VL 32B nvfp4 AWQ + 视频 VAE fp16 + 音频 VAE fp32 |
| 提示词 | < 2000 字符（MiniMax 官方上限） |
| 帧数 | 124~362（17k+5 栅格，≈5.2s ~ 15.1s @24fps） |
| 分辨率 | 复刻工作流 ResolutionSelector：宽高比 × 目标像素，32 的倍数（默认 16:9 / 0.3MP → 736×416） |
| 参考图 | 最多 9 张，prompt 里 `<Picture 1>` 引用 |
| 耗时 | 4060Ti 8G 低显存模式，5.2s 片约 5~7 分钟（采样为主） |

Agnes 后端的坑：

- **免费账号在高峰会报 `503 video_queue_full`**，这不是请求有问题，是服务端队列满。
  `agnes_video.py` 内部会退避重试 6 次（20~100s），仍失败才抛错——所以一次失败不代表
  不能出片，隔几分钟重试通常就好了。
- 判定队列是否恢复的轻量探针：`POST /v1/videos` 但**故意不传 `mode`**，回
  `400 mode is required` 说明接口正常受理（此时提交多半能过），回 `503` 说明还堵着。
  探针不建任务、不计费，但会吃一点 RPM，间隔别太密。
- 成片**自带 AAC 音轨**，后续裁剪/转码**千万别加 `-an`**。
- `size` 只能是 `720P`，改清晰度要靠 `--aspect-ratio`（换分辨率由服务端按比例给）。

**关键踩坑：DynamicVRAM 必须复刻**。ComfyUI 服务端 `main.py` 在 import torch 前
`comfy_aimdo.control.init()`，加载模型前 `init_devices()` 并把
`CoreModelPatcher` 换成 `ModelPatcherDynamic`。直调脚本若跳过这一步，VAE/CLIP 会用
静态 `ModelPatcher`——低显存下只部分上卡，`comfy.ops` 的逐 op 搬运覆盖不到
`ViT3DDecoder.register_tokens`（裸 `torch.cat` 使用），VAE 解码必崩
`Expected all tensors to be on same device ... cpu vs cuda:0`。`h3gen.py` 1b 节即
复刻这段启动序列（探针 `_vae_probe.py` 可单独验证解码路径）。

**关键踩坑：cudaMallocAsync 必须复刻**。服务端 `main.py` 在 import torch 前
`import cuda_malloc`（torch 2.x + CUDA + 卡不在黑名单时自动设
`PYTORCH_CUDA_ALLOC_CONF=backend:cudaMallocAsync`）。缺这一步，流式加载 + VAE
解码的大块激活把原生分配器打碎——reserved 几个 G 却连 30MB 都分不出，直接 OOM。
环境变量必须在 import torch **之前**设才生效。

MCP 侧两个工具：`frameseek_gen_info`（引擎状态/参数范围）、
`frameseek_generate_video`（提交生成，异步，用 `frameseek_task` 轮询）。

## 5.7 白板手绘视频（文稿 → 逐笔手绘成片）

跟 H3 生成是**两条独立的线**：H3 出的是写实画面（占 GPU、几分钟一条），
手绘出的是暖米黄纸底的逐笔动画（**本地 CPU 渲染、零 API 钱、十几秒一幕**），
两者成片都落进同一个素材库，之后一样能被搜索/导出。

底层引擎是已安装的 `whiteboard-video-studio` skill 的 `studio.py` CLI
（`~/.workbuddy/skills/whiteboard-video-studio/`），`core/handdraw.py` 把它包成
FrameSeek 的一组工具，Web 侧对应「手绘」面板。

### 六步管线

| 步骤 | 做什么 | 工具（Web 按钮） |
|---|---|---|
| 1 建工程 | 文稿（.txt）或字幕（.srt）→ 工程目录 + 拆条字幕 | `frameseek_handdraw_init`（建工程） |
| 2 分幕建议 | 读字幕，按 25~35 秒切幕，给每幕时长 | `frameseek_handdraw_scenes`（出分幕建议） |
| 3 线稿 + 标注 | 每幕一张线稿图 + **区域标注 JSON**（谁先画、画多久） | `frameseek_handdraw_annotate`（写标注） |
| 4 时间轴 | 画面总时长必须 ≥ 字幕总时长，批准后才能正式渲染 | `frameseek_handdraw_status` + `approve_timeline` |
| 5 逐幕渲染 | 本地 CPU 逐笔流式渲染 mp4 | `frameseek_handdraw_render`（渲染这一幕） |
| 6 配音合成 | Edge TTS 女声 + 本地伴奏混流，成片入库 | `frameseek_handdraw_mix`（配音合成成片） |

另有 `frameseek_handdraw_info`（引擎状态）、`frameseek_handdraw_region_preview`
（分区编号检查图）、`frameseek_handdraw_voice`（音色试听）、`frameseek_handdraw_qa`（质检）。
渲染/混流较慢，走异步：立即返回 task_id，用 `frameseek_task` 轮询。

### 为什么是分步的，不是「一句话出片」

**区域标注**（annotation）是引擎的硬前置：它决定画面里哪块先画、每块画多久。
写错了渲染直接崩或者时序错乱。这一步目前必须人（或 AI）来标——所以设计成
「标一次、渲染一次、改标注不用重来工程」的形态：同名 `scene_id` 重新
`annotate` 会覆盖标注，工程和已渲成片都保留。

未来要做全自动，路径是用本机 Ollama 的 `qwen2.5vl` 看线稿图自动出标注
（本机已有该模型，能看图），再串起生图（`handdraw-painter` + Agnes Image）。

### 标注 JSON 的硬约束（引擎 check_project 的规则，已在 `write_annotation` 前置校验）

- `sourceStartMs` 必须等于本幕之前的累计时长——多幕从 0 连续衔接；
  省略时会按已登记幕自动累加推断。
- `canvas` 必须**等于源图像素尺寸**（渲染器只对齐输出宽高，不缩放标注）。
- `sequence` 唯一且与 `startMs` 顺序一致——一支笔不能并行作画。
- 每个 `region` 必须在画布内；相邻区域 `startMs` 不能重叠；作画时长 ≥ 3 帧。
- 最后至少留 500ms 完整画面（所有元素结束 ≤ `sceneDurationMs - 500`）。
- **画面总时长（各幕 sceneDurationMs 之和）必须 ≥ 字幕总时长**，
  否则引擎报「字幕超过总画面时长」。`_check_timeline()` 会提前算出差多少秒
  并给建议；`timelineStatus` 不置 `approved` 时引擎只允许 `--preview-ms` 短预览，
  防止渲出时序错乱的废片。

### 踩过的坑

1. **引擎不覆盖同名输出**：`studio.py` 的 `new_output` 遇到已存在的路径直接
   `FileExistsError`。`handdraw.py` 统一走 `_unique_path()` 加序号
   （`scene-01.mp4` / `scene-01_1.mp4`），重渲保留旧版可对比。
2. **`studio.py` 的 stdout 有两种形态**：`check`/`init`/`mix` 输出 pretty JSON；
   `render` 输出进度行 + 末行 `OUTPUT=<路径>`。`_run()` 两种都认，
   否则渲染明明成功了却被当解析失败。
3. **SRT 是 CRLF 行尾**：按行块判空的解析会漏掉时间戳，字幕总长算成 0。
   `_cue_span_ms()` 改成正则直接扫时间行。
4. **skill 的 `.venv` 不是硬门槛**：依赖（cv2/numpy/av/PIL）装在 WorkBuddy 的
   主 venv 里时引擎照样能跑，`engine_info()` 只在依赖真缺时才报 not ready。
5. **手绘产物不在 `.frameseek/cache` 里**，`/media` 端点会 403（它只允许
   cache 目录内的相对路径，防目录穿越）。新增 `/hd/media`，限定「目标库目录内」
   才放行，前端 `hdMedia()` 用它而不是 `mediaUrl()`。

### 给 LLM 用的设计（2026-10-17 补齐）

工具面从 29 扩到 **33 个**，并按「模型能不能自己走通」重做了一遍：

**① 参数级说明**——以前所有参数只有名字没有解释（靠函数 docstring 顶着），
`pre`/`post`/`fast`/`line_ids` 这类只能靠猜。现在全部走
`Annotated[T, Field(description=...)]`，写进 `tools/list` 的 `inputSchema`。
`use_asr` 这种历史命名在参数说明里直接写明真实语义。

**② 错误返回带 `hint`**——以前只回「在 xxx 里找不到台词 123」，模型只能重试同一个
调用。现在回「该调哪个工具、该带什么参数」。撞号（id 跨库不唯一）是最高频的坑，
hint 里专门点明。

**③ 新增 4 个工具**：

| 工具 | 为什么有 |
| --- | --- |
| `frameseek_doctor` | 一次给全：引擎可用性 / 每库状态 / 在跑任务 / `problems` 清单。原来要连调 3~4 个工具拼 |
| `frameseek_find_videos` | **认片名**跨库找片。原来只有认台词的 `search`，用户说「找一下潜伏第三集」就没辙 |
| `frameseek_video_summary` | 一次拿到元信息 + 台词全文，`video_info` + `get_lines` 两步合一，按字数截断省 token |
| `frameseek_list_clips` | 已导出片段清单（含 Web 端导的）。原来导完就找不到文件在哪 |

**④ `export_clip` 补齐功能缺口**——`subtitle=true` 烧字幕（对齐 Web 端
`/api/clip` 已有能力）、`line_ids` 批量导出、`pre/post` 加范围校验。

**⑤ 资源层**（`resources/list` 可读，5 个）：

| URI | 内容 |
| --- | --- |

**烧字幕按台词来源自动分流**（Web `/api/clip` 与 MCP `export_clip` 共用
`core/media.py` 的 `decide_burn`，只有这一处判定规则）：台词来源是 `ocr` 说明

## 8. 剪辑向的实际用法

搜到台词 → 点 **±片段** → 打开 `.frameseek\clips\` → 拖进剪映/PR。  
默认"秒切"（`-c copy`）是秒出，可能有零点几秒误差；要帧精确就取消勾选（重编码，慢一些）。  
批量导出：多条台词一起选还没做界面，MCP 侧可以循环调 `frameseek_export_clip`。
